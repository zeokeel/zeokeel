## 0. 结论速览

### 0.1 直接回答两个问题

| 问题 | 回答 | 关键证据 |
| --- | --- | --- |
| **Q1：用 mygo 原生实现、不搞这么多视觉效果，能减少很多代码工作量吗？** | **能省，但不是"腰斩"，而且"视觉效果"不是省的主要来源。** 现有 UI 生产代码 17,121 行可净省 **5.2k–7.9k 行（30%–46%）**；测试可再减 **4.3k–5.1k 行（UI 测试 29%–34%）**。但 UI 只占全仓生产代码 35%，所以**全仓只减 10%–13%**。一次性迁移 **12–20 人日**（+ 品牌层 3–5 人日）。真正的大收益在**增量**：以后每新增一屏 150–300 行（原生）vs 1,100–1,300 行（现状），且不再背 106MB 基线与像素门禁。 | [01 §0/§5](01-code-audit.md)、[02 §5](02-mygo-native.md) |
| **Q2：从 UI/UX 设计角度，这样是不是更好？** | **交互层：明显更好，且应该做**（桌面菜单栏/通知/可选中文本/滚动条/系统字号、高对比、IME/DPI、控件键盘与 a11y 全覆盖都是现实现的系统性缺口）。**视觉层：不该"不搞视觉"，而该"不再以像素对齐为目的"**——DSH 的观感不是靠特效，而是几何/控件形态/字体/图标；保留已有视觉语言（或换成自有品牌视觉）是产品决策，不是工作量问题。 | [03 §2/§5/§10](03-ux-design.md)、[02 §4](02-mygo-native.md) |

### 0.2 三个必须纠正的前提（否则会做错决策）

1. **现在的 UI 已经是"mygo 原生"**：100 处 import `mygo/ui`，无 webview/HTML/CSS 运行时（C2 约束成立）。所以"用 mygo 原生实现"不是架构切换，**只是"用不用原生控件/默认外观"的差别**。"换成原生"不是换技术栈，是换实现方式。
2. **"视觉效果"根本不是成本大头**：DSH 的设计系统是克制的（**20 个颜色、5 组阴影、14 个字号、16 个圆角**；渐变只用于滚动淡出遮罩/加载环等局部功能——46 处 `linear-gradient` 遮罩 + 3 处 conic 加载环，无毛玻璃/无大面动效）。我们的实现里阴影 16 处、渐变/模糊 0 处、`Element.Transition(` 仅 1 处，动效层 `design/motion.go` 35 个导出中 **22 个在包外零引用**——大部分是"研究完没人用"的 1:1 副产品 [02 §2.3]。成本在**几何/控件形态/字体/图标/功能面**，不在特效。
3. **"像素 1:1"实际上早已不是门禁**：像素测试只渲染静态 `App{Ctrl:nil}` 假屏，真实 UI 从未进入像素门禁；落地预算已放宽到 masked **2.0%–8.5%/屏**（PLAN 要求 0.2%，松 10–42 倍），暗色/窄屏 6.2%–23% 且预算=实测+3pp；~85% 残余差异是文本抗锯齿地板，原理上不可消除 [01 §4.2]。**继续投入是在拟合一个不反映真实体验、也不可验收的数字。**

### 0.3 一句话建议

> **立即止损（半天级）：把"和 DSH 像素对齐"从验收目标降级为参考资料；把交互按桌面平台惯例做；用 mygo 原生控件逐步替换手搓控件（从 markdown/侧栏/列表开始）。视觉方向（保留 DSH 视觉语言 vs 原生+自有品牌）是产品定位决策，建议放在第二阶段拍板，不要用一次大重写来回答它。**

## 2. 前提纠正：三个"原生"与"视觉效果"的真相

### 2.1 三个不同的"原生"（用户的话里混在一起了）

| 概念 | 含义 | 现状 | 换它的收益 |
| --- | --- | --- | --- |
| **原生控件** | 用 mygo `ui` 的高层控件（Sidebar/List/Tabs/Collapsible/Select/markdown/Toast…）而不是自己用 `Text/Row/Column/Box` 拼 | **几乎没用**：`ui.Sidebar/Select/Tabs/Collapsible/Table/Tree/List/MenuButton/Toolbar/Badge/…` 调用数**全为 0**；1,169 次 `ui.*` 调用中 72% 只是布局图元 [02 §2.1] | **最大**：省 5.2k–7.9k 行 + 免费获得键盘/焦点/a11y/IME/DPI/虚拟列表/流式 markdown |
| **原生默认外观** | 用 `ui.LightTheme()/DarkTheme()` 默认样式，不逐像素定制 | 现全部按 DSH 令牌手调（design 层 752 行 + 2,833 个样式 setter） | **小**：视觉从"像 DSH"变成"另一个产品"，要品牌层（300–600 行）才达到产品级观感 [02 §4.2] |
| **原生交互/平台惯例** | 系统菜单栏、通知、文本选择、系统滚动条、窗口状态、系统字号/高对比、独立设置窗口 | **系统性缺失**：`App.SetMenu` 0 处、`Selectable(` 0 处、`Scrollbars(` 0 处、无系统通知、无窗口状态持久化、`TextScale/HighContrast` 未接线 [03 §2.2] | **大**：这是"像不像桌面应用"的关键，也是迁移用户长期最在意的部分 [03 §5] |

> 结论：用户想解决的痛点主要是第 1、3 项；第 2 项（换成默认外观）只是视觉方向选择，**不是省代码的主要杠杆**。

### 2.2 "视觉效果"在代码里到底有多少

| 事实 | 数字 | 出处 |
| --- | --- | --- |
| DSH 设计系统规模 | 20 色 / 40 背景 / 5 组阴影 / 14 字号 / 16 圆角 / 4 字体族 | `baseline/css/summary.json` |
| 现实现视觉特效 | 阴影 16 处；渐变 0；模糊 0；`Element.Transition(` 全 shell 1 处；动效预设 35 个导出中 22 个零引用 | [01 §2.1](01-code-audit.md)、[02 §2.3](02-mygo-native.md) |
| 样式层代码 | `internal/design` 752 行、`internal/pixeltest` 140 行、静态五屏 2,042 行 | [01 §1.2/§5.1] |
| 反直觉实验 | 只改约 20 个主题字段（18 色 + 圆角），像素只变动 **0.60%** | [02 §4.3]（`go run ./.probe/research/native-demo/analyse` 可复跑） |

**含义**：想让 UI "少搞视觉效果"，能删的是设计令牌层、静态假屏、像素工具和动效研究层（约 3.8k–4.5k 行）；**剩下的 10k+ 行是功能 UI 与交互接线，任何方案都跑不掉**。而"DSH 长什么样"的成本主要花在几何常数、控件形态、字体与图标上——这正是 02 报告"换 18 个颜色只改 0.60% 像素"要说明的事。

## 3. 现状量化：16.3k 行 UI 与 106MB 基线的成本结构

### 3.1 代码与资产（实测，2026-11-05）

| 项 | 数值 | 占全仓 |
| --- | --- | --- |
| 全仓 Go（`cmd`+`internal`） | 生产 **49,363** / 测试 **44,725** 行；838 个 Test 函数 | 100% |
| UI 层生产 | `shell` 16,288 + `design` 752 + `icons` 81 + `pixeltest` 140 = **17,261** | **34.6%** |
| UI 层测试 | `shell` 14,514 + design/icons/pixeltest 302 = **14,816** | **33.1%** |
| `internal/shell` 单包 | 生产 16,288 / 测试 14,514（测试占 47%） | 32.7% / 32.5% |
| 对齐资产 | `baseline/` **605 文件 / 106MB**（80 截图 + 53 份逐元素 CSS 63MB + 74 控件 dump + 108 条行为/384 张对比图）；`artifacts/` 8.9MB；全仓 647–662 张 png；`scripts/cdp.mjs` 509 行 + 25 份 capture dump；`docs/baseline/` 1,222 行 | — |
| CI 成本 | 每次多跑 **6 次** shell 像素测试；shell 包全量 **39–41s**；`baseline/VERSION` 缺失（基线未锁版本） | — |

### 3.2 像素门禁的真实状态（建议全文最该看的一节）

- 目标（[PLAN §1.2](../PLAN.md)）：非文本区 ≤ 0.2%/屏、文本区 SSIM ≥ 0.98、几何偏差 ≤ 1px。
- 落地（[01 §4.2](01-code-audit.md)）：masked 预算 home 2.0%、session **8.5%**、plugins 4.5%、settings 4.2%、automation 2.2%；dark/narrow 预算 = 实测 + 3pp（6.2%–23%）。
- 实测（可复跑）：浅色 masked 0.93 / 6.03 / 2.90 / 2.28 / 1.18%；dark 6.42 / 19.39 / 2.98 / 2.80%；narrow 6.86 / 18.44%。
- 结构性问题（3 条，均有 `file:line`）：
  1. **只测 static 假屏**：`TestScreensBaseline` 渲染 `&App{Ctrl:nil}`，生产恒走 live（`internal/app/app.go:101`），**真实用户看到的 UI 没有像素门禁**；
  2. **不可达**：~85% 残余差异是 Chromium subpixel AA vs mygo 灰度 AA 的渲染器地板（`docs/STATUS.md` 已量化），容差放大到 48 仍有 4.5%+；
  3. **指标不可解释**：门禁预算被反复放大到"实测值+余量"，已从"验收 1:1"退化成"布局不继续变坏"的回归检查。

> 结论：**"1:1 像素"不是"还没做到"，而是在当前渲染栈上不可达、且没有可执行的验收器**。继续投入不会有收敛点（[docs/QUALITY.md:3-7](../QUALITY.md) 记录的"验证代理找不到问题→每轮都有新问题"就是这个症状）。

### 3.4 也要承认的成绩（不是"路线失败"，是"路线不可持续"）

- 2 天内把 5 屏 UI（Home/Session/Plugins/Settings/Automation）用纯 Go 无 webview 做出来，且能无头渲染、无头交互测试、进 CI——这本身是可行性红利，**mygo 的 `ui.Render` + `ui.NewTester` 是这个项目最重要的资产**，任何新方案都应继承。

## 4. mygo 原生方案实测：能做什么、能省多少

### 4.1 原型（可运行证据）

- **294 行**原型（240 代码行，其中视图构建函数 135 行）：Home 全屏 + Session 消息流小样（markdown 回复、可折叠工具卡、可拖拽 Split、Tabs 右栏、明暗双主题）。
- 零像素手调、stock 主题零自定义颜色；44 处样式调用全部走 `t.Space/t.Rem/t.Radius/t.FontSize` 主题令牌。
- headless `ui.Render(...,scale)` 出图 12 张；`go run ./.probe/research/native-demo` 可复现；分析工具复跑的数字与报告一致。
- 免费获得（不用写）：侧栏键盘选择/首字母跳转/树形 a11y、工具栏溢出、Tabs 键盘、Collapsible 展开动画、列表虚拟化、markdown 流式渲染 + 代码块 Copy、焦点环/hover/按下/禁用态、明暗主题、系统字体、DPI 缩放、`ui.NewTester` 无头交互测试。

### 4.2 现状在"重造哪些 mygo 已有的轮子"

| mygo 原生能力 | ZeoKeel 现状 | 差距 |
| --- | --- | --- |
| `ui/markdown`（3,423 行，含流式/表格/数学/复制） | 自研 `internal/shell/markdown.go` 628 行，无流式、无复制变体 | **可整体删除** |
| `ui.Sidebar`（Finder/Mail 式，键盘/首字母/a11y tree） | `workspaces.go` 1,232 行 + `sidebar_hover.go` 118 行手搓 | 大量可删 |
| `ui.List`（虚拟化） | 消息流/插件行/设置行全手搓，无虚拟化 | 大量可删 |
| `ui.Collapsible` | `toolcards.go` 479 行手搓折叠/状态点 | 部分可删 |
| `ui.Select/MenuButton/Combobox` | 权限/模型/工作区 chips 与命令面板 ~1,200 行手搓 | 大幅缩减 |
| `ui.Tabs/Toolbar/Badge/PrimaryButton` | 手写 tab 条/工具栏/药丸/主按钮 | 可替换 |
| `ui.Transition/Animate` | `design/motion.go` 313 行，35 导出 22 个零引用 | 基本可删 |
| `mygo/i18n`（CLDR 复数/日期） | `i18n.go` 589 行（350 键文案表 + 语言匹配逻辑） | 文案表保留，逻辑可减 |

**产品侧含义**：这不仅是代码量问题——**用 mygo 自带控件意味着键盘、焦点、无障碍、IME、DPI、列表虚拟化这些"桌面应用基本功"随控件免费拿到**；手搓控件等于把这些全部自己实现一遍（并已在 verifier 里暴露：键盘焦点 8 项失败）。

### 4.3 代码量：已有 / 增量 / 测试

| 口径 | 数字 | 出处 |
| --- | --- | --- |
| 从现有代码净省（生产） | **5,250–6,900 行**（01 自下而上）/ **5,657–7,890 行**（02 函数级外推），收敛后建议引用 **5.2k–7.9k = UI 生产 30%–46%** | [01 §5.4]、[02 §5.2] |
| 占全仓 | **仅 10.6%–14.0%**（UI 只有 35%）——**"腰斩"不可能** | [01 §0] |
| 测试可减 | **4,300–5,100 行**（视觉/几何/对比度/a11y 专项 2,341 + 修-验循环 3,065 的 60–85%） | [01 §3.4/§5.1] |
| 全仓 Go 净减 | ~9,550–12,000 行 = **10.2%–12.8%** | [01 §5.4] |
| 增量成本（真正的收益） | 新屏原生 **150–300 行** vs 现状 **1,100–1,300 行**（Home 实测 1,137 行，原生同屏 ~100 行视图代码） | [02 §5.1/§5.3] |
| 一次性迁移 | **12–20 人日**（删 0.5–1d + 替换 8–14d + 回归验收 3–5d）+ 品牌层 3–5 人日（若要原生外观） | [01 §5.4]、[02 §6.1] |

> 与 03 报告的"工程量省 20%–30%"不矛盾：**代码行可减 30%–46%，但重写本身有成本**，净收益主要出现在后续增量与维护上。

### 4.4 视觉：原生默认"够用但不像 DSH"，DSH 观感买不到

（图见 [compare-home-4up.png](../../.probe/research/out/compare-home-4up.png)：左上 DSH 基线、右上现实现、左下原生默认、右下原生+DSH 令牌）

- raw 像素差异（容差 12/255，未掩码）：现实现 **1.18%**、原生默认 **3.27%**、原生+DSH 令牌 **3.65%**——数字看着只差 2pp，但截图一眼是**两个产品**（图标、控件形态、密度、字体全不同）。
- **关键实验**：同一布局下只改约 20 个主题字段（18 色 + 圆角）只改动 **0.60%** 像素 → **颜色/圆角是"像不像"最便宜的部分；贵的是几何、控件形态、字体、图标**。
- 因此：
  - 若目标是"DSH 观感"：需要品牌层（图标库/字标/2–3 个组合控件/约 30 行主题），估 300–600 行 / 3–5 人日 [02 §4.2/§6.2]；
  - 若目标是"独立桌面产品"：原生默认 + 品牌层就是 80→90 分起步，**不需要为像 DSH 付 16.3k 行**；
  - **不要用 raw 像素 diff 衡量"换设计"的代价**——它在白底画面上会严重低估观感差异。

### 4.5 代价与风险

- mygo v0.7.4 仍是 0.x，API 可能变动 → 锁版本 + 适配层（现有 `internal/shell` 与 `ui` 的直接耦合会随迁移变化，需控制爆炸半径）。
- 迁移是**重写不是开关**：焦点顺序/键盘可达/hover/展开态/虚拟化要重新接；不过原生控件自带这些，工作量主要在数据接线与产品定制。
- 功能/交互接线约 **10.3k–12.1k 行（UI 生产 60%–70%）必须保留并迁移**，不会消失 [01 §5.3]。
- 短期可能是负收益：12–20 人日迁移 + 回归风险；回本点取决于后续 UI 变更量。
- 无 git → 迁移前必须先 `git init`（EVOLUTION G1 已列为 P0）。

## 5. UI/UX 判断：原生化好在哪、险在哪

### 5.1 现状是"能在桌面窗口里跑的 Web UI"

| 级别 | 问题 | 证据 |
| --- | --- | --- |

### 5.2 外部证据（14 个来源，详见 [03 §4](03-ux-design.md)）

- **GNOME HIG**：hover 不应作为揭示操作/关键信息的唯一方式；所有指针操作都应可键盘完成。
- **Microsoft Commanding basics**：命令放对 command surface（菜单栏/命令栏/上下文菜单）；可撤销的给 undo，不可撤销的给确认。
- **Apple**：自绘控件只在平台没有时建议；自绘必须补平台行为。
- **Raycast 工程博客**：让 web app 在桌面"变味"的最快方式是沿用 web 惯例——不 cursor:pointer、不 hover 高亮、Settings 用独立原生窗口、popover/tooltip 用原生窗口。
- **NNG**：一致性分内部与外部（平台惯例）；Aesthetic-Usability Effect 说明"好看"会**掩盖**交互缺陷——只看像素相似会误判体验。
- **W3C WCAG 1.4.13**：hover/focus 触发内容必须可关闭、可悬停、可持续，且可 focus 触发。
- **Zed / Daring Fireball（Claude=Electron vs ChatGPT=AppKit）**：桌面 AI 产品原生/混合路线并存且被用户认可；自绘/原生是正当差异化。
- **同类产品**（Claude Desktop、ChatGPT、Cursor、Windsurf、Zed、Warp、Raycast）：没有"桌面 Agent 必须长成 Web 聊天页"的共识；主流要么原生、要么混合但强本地化。

> 关于法律：DSH 是 MIT 开源项目（`@deepseek-ai/dsh` **package license: MIT**），且本项目基线文档明确"不复用 DSH 代码与资源、图标等价重绘、字体用 OFL"；trade dress 讨论在 03 报告中已按"不构成法律意见"谨慎处理。**品牌/文案去 DSH 化更多是产品与品牌问题，不是主要法律障碍**。

### 5.3 "视觉相似 vs 交互相似"：迁移用户长期看交互

- 短期（前 3 秒）：视觉相似提供识别与信任（保留视觉语言有价值）。
- 长期（第 2 天起）：交互决定留存——用户记住的是"菜单在哪、能不能选、通知有没有、键盘能不能全走通"。
- 更关键：**当前实现连"像 Web 一样交互"都没做到**——浏览器替用户提供的文本选择、右键菜单、滚动条、系统通知被丢掉了，只保留了 Web 的外观。03 报告称之为"像一张 Web 截图一样交互" [03 §5.1]。
- 因此：**视觉语言可以保留（熟悉感），交互必须本地化（可用性）；两者不冲突。**

## 6. 方案对比与推荐

| 维度 | **A. 维持三重 1:1（现状）** | **B. 视觉语言保留 + 去像素门禁 + 交互本地化** | **C. 全面原生重设计（原生默认外观 + 自有品牌）** |
| --- | --- | --- | --- |
| 视觉 | 100% 像 DSH | 接近 DSH（保留令牌/几何/密度） | 新 ZeoKeel 视觉（品牌层 300–600 行） |
| 桌面体验 | 一般（Web 交互模型） | 好 | 最好 |
| 差异化 | 无（DSH 桌面复制品） | 中 | 高 |
| UI 代码 | 0 节省，持续付基线/像素成本 | 省 2k–3k 行（仅删对齐层）+ 控件替换可更多 | 省 5.2k–7.9k 行（30%–46%） |
| 一次性成本 | 低（但持续） | 低–中（1–2 周交互 P0 + 渐进替换） | 中（12–20 人日 + 品牌层） |
| 风险 | 像素不可达/DSH 发版漂移/品牌法务边缘 | "像 DSH 但操作不同"的认知落差 | 迁移识别度下降、回归风险、短期负收益 |
| 适用前提 | ZeoKeel = DSH 官方/半官方桌面壳 | 面向 DSH 用户的桌面替代品（6 个月内交付） | 独立品牌/长期产品；mygo 能力演示 |

**推荐：以 B 为第一步、A 的"原生控件替换"作为并行工程手段、C 作为视觉方向的可选第二阶段。** 理由：

1. **不要用一次大重写来回答视觉方向问题**——先把不可持续的验收体系去掉（半天），再按增量替换控件（1–2 周），视觉方向放到第二阶段拍板。
2. **交互本地化没有争议**：无论视觉选 B 还是 C，P0 交互都必须做；它不依赖视觉决策，且直接解决"灾难感"里最真实的部分（用户每天碰到的体验）。
3. **原生控件替换独立于视觉方向**：markdown/侧栏/列表/工具卡换成 mygo 控件，代码立省、键盘/a11y/IME/DPI 立刻变好；保留 DSH 令牌时视觉变化可控（02 已证明"换 18 色只改 0.60% 像素"——反过来，保留令牌也不需要很多行）。
4. **C 的完整重写是 12–20 人日 + 回归，且现在做要同时承担视觉与交互两个风险**；B 完成后若要做独立品牌，再迁移视觉（02 的"品牌层 300–600 行"路径）即可，不必推倒重来。

> 注意：02 报告在自己语境下推荐 A（原生控件+品牌层），03 推荐 B；两者其实不冲突——**A 是"控件与视觉实现方式"，B 是"产品视觉策略"**。本报告把两者拆开：控件/交互原生化（A 的工程部分）立即做；视觉是否去 DSH 化（B vs C）待产品定位拍板。

## 7. 建议落地路线（可回滚、分阶段）

### Step 0 · 止损与治理（0.5–2 天，零风险）

1. **`git init` + 首次提交 + tag**（当前仓库无 git，任何迁移前必须先做；同时补 `.gitignore`：`.cache/`、`dist/`、`zeokeel*`、`.probe/`、`artifacts/` 视需要）。
2. **像素门禁降级**：`scripts/ci.sh` 移除 6 次像素调用；`TestScreensBaseline`/`TestScreensDarkNarrow` 改为 `t.Skip` 或移入 `-tags visual` 的可选手动任务；CI 只保留功能/交互/令牌一致性/`ui.Render` 冒烟。
3. **基线归档**：`baseline/` 压缩为只读参考（可移出主仓库或放 `docs/archive/`），写 `baseline/VERSION`；`docs/baseline/` 标记"历史参考，不再是验收标准"。
4. **口径修正**：README/PLAN/STATUS 中"像素/交互/功能三重 1:1"改为"DSH 风格视觉 + 功能对齐 + 桌面原生交互"；把"1:1"从对外承诺中移除。
5. **静态五屏处理**：生产恒走 live，静态五屏只被测试 fixture 使用——随 Step 1 迁移逐步删除（需同步改 23 个测试文件，工作量小）。

### Step 1 · 交互 P0 + 第一批原生控件（1–2 周）
