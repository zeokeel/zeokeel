# Grok Bot 开源实现：交互设计规格（人以人为中心版）

> 状态：**设计稿，待审**。与 [grokbot-open-source-plan.md](grokbot-open-source-plan.md) 配套：那份讲机制，这份讲**人看到什么、能做什么、做完之后世界怎么变**。
> 先读 §0 的三条自我修正，那是这份文档存在的理由。

---

## 0. 上一版规划的盲区（先认错，再设计）

| 盲区 | 具体表现 | 这份文档的修正 |
|---|---|---|
| **机制先行** | 我写了租约、CAS、状态机，却没写"人第一次打开这个软件看到什么" | §4 的 S1 从**首次启动**开始，每个场景都写清"他看到什么" |
| **忘掉人的时长** | 我按"用户有 1 小时研究界面"来设计，实际上你在**地铁上只有 30 秒** | §1 定义三种时长模式，§8 审批按"10 秒完成"设计 |
| **忘掉"我不在"** | 我设计了通知，却没设计"离开 8 小时后回来，怎么一眼看懂发生了什么" | §4 S11 与 §7 的"回来视图" |
| 忘掉失败的人 | 只写"转 blocked"，没写**人被卡住时该看到哪句话** | §5 状态矩阵 + §11 文案词典：每个失败态都有"下一步" |
| 忘掉撤销 | 只写审批通过，没写"手滑批错了怎么办" | §8.4 误批更正、§4 S12 撤销与改期 |
| 忘掉打扰预算 | 通知只有渠道，没有"一天最多打断几次" | §7.2 打扰预算（默认 ≤5 次/天） |
| 忘掉语言 | 满屏"任务、租约、子会话、CAS" | §6 任务卡三行规范 + §11 禁用词表 |

> 结构性的补救：**§13 完整性矩阵**（事件 × 谁看到 × 在哪 × 能做什么）和 **§12 验收清单**。以后每次改功能，先过矩阵再写代码——这是防"容易遗忘"的机械手段，不靠记性。

## 1. 人的模型

### 1.1 三种时长，三种界面

| 模式 | 时长 | 场景 | 设计目标 | 主界面 |
|---|---|---|---|---|
| **30 秒** | 地铁/电梯 | 只想知道"有没有事等我"、批一个卡 | 一屏一单，三个动词，不需要滚动 | 手机 IM 审批卡 / `/inbox` 首屏 |
| **5 分钟** | 会议间隙 | 派一个活、看一眼进度、改一句话 | 两次点击内完成派活；进度用三行话说清 | `/` Now + `/team` |
| **1 小时** | 晚上复盘 | 看今天干了什么、错在哪、要不要沉淀成技能 | 时间线 + 证据 + 一键沉淀 | `/team` 时间线 + 任务详情 |

**硬性要求**：任何"需要你决策"的东西，都必须在 30 秒模式下可完成；做不到就说明设计错了，不是用户没耐心。

### 1.2 一天的五个真实时刻

1. **早上 8:40**：打开电脑，想确认昨晚挂机的活有没有出事 → 需要"你不在的 12 小时"摘要。
2. **9:20 地铁**：微信弹出一条审批"给客户发报价单" → 需要 10 秒内看懂并决定。
3. **11:00 会议间隙**：想起一件事，语音发一句"把上周竞品价格整理成表" → 需要它自己拆解、别来烦我。
4. **15:30 被卡住**：队友缺一个 API key → 需要一条消息告诉我"缺什么、给了就能继续"，而不是"任务失败"。
5. **21:00 复盘**：想知道今天谁干了什么、花了多少、有没有需要沉淀的经验 → 需要时间线而不是日志。

### 1.3 人的痛点（设计要消灭的）

- 看不出来"现在到底有没有事等我"（入口分散）。
- 审批卡信息不够，得点进去才知道批什么（盲批或不敢批）。
- 队友在干什么说不清，只有"运行中"三个字。
- 失败了只有红字，没有"我该怎么办"。
- 离开半天回来，要先读 200 条消息才知道发生了什么。
- 手机上只能看不能批，还得回电脑。
- 误操作不可逆，或者撤销按钮藏在三层菜单里。

## 2. 六条交互原则

1. **一处等我，一处在跑**：人只需要记住两个地方——`/inbox`（需要我的）和 `/team`（在跑的）。其他屏都是这两个的下钻。
2. **打扰有预算**：默认每天最多 5 次主动打断（审批除外，审批是阻塞项）。其余进汇总。
3. **说人话**：面向人的界面不出现"租约、CAS、子会话、token 预算"这类词；出现即视为缺陷（§11 有禁用词表）。
4. **每个失败都给下一步**：任何错误态必须带一个可点的动作（重试/换渠道/我手动来/放弃）。
5. **可撤回**：草稿可改、任务可取消、误批 30 秒内可更正；不可撤回的动作要在按下前说清。
6. **状态不美化**：进行中就是进行中，等待就是等待，卡住就是卡住；不允许用"运行中"掩盖"其实在等你"。
7. **一个收件人**：所有渠道的消息都先给 Lead，只有 Lead 对你说话；你在哪个 App 里回，都不改变这条。
8. **两种回法都算数**：点按钮，或回一句「同意/不同意」——不强迫你学一套新交互。

## 3. 信息架构

### 3.1 人只认两层

```
第 1 层（每天看）       /            现在     —— 一句话状态 + 输入框
                      /inbox       等我     —— 只有"需要你"的东西
                      /team        在跑     —— 谁在干什么、卡在哪
第 2 层（下钻）        /c/:id       会话     —— 与 Lead 的对话
                      /t/:taskId   任务详情 —— 一单任务的完整一生
                      /c/:id/files 产物     —— 这次会话产出的文件
第 3 层（偶尔）        /settings/*  设置
```

**新增最小**：`/t/:taskId`（任务唯一深链，从任何地方点任务都到这里）、`/settings/connectors`、`/settings/bots`；其余复用现有路由，不新建屏。

### 3.2 每个屏只回答一个问题

| 屏 | 只回答 | 不做什么 |
|---|---|---|
| `/` | "现在有没有事、我该说什么" | 不展示全部任务、不展示统计 |
| `/inbox` | "有什么在等我" | 不展示"仅告知"的信息（那些在 `/team`） |
| `/team` | "谁在干什么、卡在哪" | 不做审批（审批只从 `/inbox` 或 IM 进） |
| `/t/:taskId` | "这一单到底怎么回事" | 不承载跨任务操作 |
| `/c/:id` | "我跟 Lead 说到哪了" | 不展示队友的内部过程（折叠在任务卡里） |

## 4. 场景脚本（S1–S12）

> 每条都按同一结构写：**他在哪 → 他看到什么 → 他能做什么 → 系统怎么回应 → 失败分支 → 文案**。
> 文案是产品的一部分，直接可抄进 `web/src/i18n/zh.ts`。

### S1 首次启动（90 秒内必须能用）

- **他在哪**：第一次打开 Web 界面，什么都没配。
- **他看到**：一句人话 + 三个选择，不是设置向导表格。
  > 你的电脑现在是"大脑"，它需要一张嘴和一双眼睛。
  > ① 绑定微信（推荐，手机上也能批）② 绑定钉钉 ③ 先不绑，只用网页
- **他能做**：点一个 → 出现二维码/授权按钮 → 成功后显示"已连接，发一句试试：帮我看看今天的日程"。
- **系统回应**：绑好后立刻自动建一个"助理"岗位（不需要他先学"岗位"概念），并把示例任务放进输入框（未发送）。
- **失败分支**：扫码超时 → "二维码过期了，点这里换一张"；平台拒绝 → "微信这边没通过，通常是账号没开通该功能，点这里看说明"。
- **不做**：不出现"配置 Bot 模板 / 工具白名单 / 预算"这些概念；它们在第 4 次使用后才在设置里出现。

### S2 发第一个任务（30 秒）

- **他在哪**：`/` 或微信私聊。
- **他看到**：一个输入框，placeholder 是"让谁做什么，什么时候要"。
- **他能做**：打字/语音/拖文件，回车发送。
- **系统回应（关键）**：**不等拆解完才回应**。0.5 秒内先把他的话原样回显成一条"收到"，然后 Lead 开始拆解，进度以一行字更新：
  > 收到。我拆成 3 步：抓价格 → 清洗 → 出表。要我现在开始吗？〔开始〕〔先说说你的想法〕
- **设计理由**：人对"我发的消息有没有被接住"极其敏感；先回声，再思考。
- **失败分支**：模型不可用 → "我这边模型连不上，你的话我存着，恢复后自动继续"（不是"发送失败"）。

### S3 拆解确认：默认不打扰，越权才问

- **默认**：Leads 自己拆完直接开工，只在 `/team` 显示进度。理由：你说了只有大事才找你。
- **必须问你的两种情况**：
  1. 涉及对外发送/花钱/删数据 → 走审批（S5），不在这里问；
  2. 拆出来的活超过 5 个子任务或预计超过 2 小时 → 一行征询：
     > 这活比我想的大（5 步、约 2 小时）。〔就这么干〕〔砍一半先做〕
- **他看到**：一行字 + 两个按钮，不弹模态。

### S4 任务进行中（人看到什么）

- **他在哪**：`/team`，或 `/` 顶部一行。
- **他看到**：每个任务一张卡，**只有三行**：
  ```
  研究竞品定价            进行中 · 数据 Bot · 12 分钟
  正在抓 3 个站点，已完成 2 个
  不需要你做什么
  ```
- **他能做**：点开看证据与产物；点"催一下"（给 Lead 发一句）；点"停"（取消，保留已完成部分）。
- **系统回应**：状态变化即时反映；超过预计时间 50% 时卡片变"比预计慢"，而不是继续显示"进行中"。
- **失败分支**：队友失联 → 卡片显示"队友掉线，10 分钟后自动重派"，不需要他点。

### S5 审批（10 秒，桌面与手机同构）

- **他在哪**：微信/钉钉/飞书推送，或 `/inbox` 第一条。
- **他看到（手机，一屏不滚动）**：
  - 微信里是一段纯文本 + 一个可点链接（「点开就能批」），没有按钮；
  - 钉钉/飞书里是能点的卡片，三个按钮与桌面文案一致；
  - 点开后是**手机审批页**：一屏、三个大按钮、一个后果句；
  ```
  需要你批准 · 2 分钟前
  给「张三」发报价单邮件（含附件 3 个）
  发出后无法撤回。收件人：zhang@acme.com
  〔允许〕〔始终允许〕〔拒绝〕
  回复 #A3 允许 · #R3 拒绝
  ```
- **他能做**：点按钮 / 回短码 / 忽略（15 分钟后换渠道再提醒）。
- **系统回应**：立刻回执"已允许，正在发送"；完成后补一条"已发出，回执见任务"。
- **失败分支**：
  - 发送失败 → "邮件没发出去（对方服务器拒收）。要我换一种方式吗？〔重试〕〔改成附件链接〕"
  - 短码过期 → "这条已经过期了，我重新发一张〔重发〕"
  - 不是本人回复 → 静默忽略，不回复（避免暴露系统存在）。

### S6 队友卡住，需要你补东西

- **他在哪**：`/inbox`，优先级高于普通进度。
- **他看到**：
  ```
  卡住了 · 研究 Bot 需要 GitHub 只读令牌
  给我之后我继续；不给的话我可以改用公开搜索（会慢一些）
  〔去填令牌〕〔改用公开搜索〕〔停掉这个任务〕
  ```
- **设计要点**：**永远给"不给你也能继续"的降级选项**，否则人会觉得被要挟。
- **失败分支**：他选了"去填令牌"但中途放弃 → 24 小时后自动走降级方案，并在汇总里说明。

### S7 完成：Lead 自审之后给你什么

- **他在哪**：`/c/:id` 里的完成卡（不是 `/inbox`，除非标了"需要你确认"）。
- **他看到**：
  ```
  做完了 · 竞品定价表（3 个站点，42 条）
  结果：定价表.xlsx（点开预览）｜证据：3 个来源链接、2 张截图
  我没能确认的：站点 B 的价格需要登录，用的是缓存页
  〔打开表〕〔让他们再核一遍〕〔存成技能〕
  ```
- **系统回应**：点"存成技能"→ 生成草稿（六段式），你确认后入库；下次同类任务更快。
- **失败分支**：验收被 Lead 判不合格 → 卡片显示"我打回了：缺来源链接"，并已自动重派，不需要你介入。

### S8 失败与超预算

- **他看到**（任务卡三行不变，颜色与第三行变）：
  ```
  抓取站点 B              失败 · 数据 Bot · 9 分钟
  站点返回 403，重试 3 次都被拦
  〔换浏览器方式再试〕〔跳过 B 先出表〕〔停掉〕
  ```
- **超预算**：
  ```
  这一步花掉了 82% 的预算（约 4.1 万 token），还要继续吗？
  〔继续，再加 5 万〕〔收尾，用现有数据〕
  ```
- **设计要点**：预算用"人话单位"（"大约 4 万 token / 预计再花 3 分钟"），不显示原始计数器。

### S9 外部事件进来（微信/钉钉/飞书/邮件）

- **他在哪**：正在开会，群里有人 @ 机器人："帮我查下上周的退款率"。
- **系统行为**：消息进收件箱，**不回复、不执行**（避免在群里乱说话）。
- **他在哪看到**：`/inbox` 里一条"外部消息待处理"，以及（如果开了）汇总推送：
  > 钉钉 #运营 有 3 条在等你决定：查退款率 / 客户投诉跟进 / 周报模板
  > 〔全部看一遍〕〔只处理第 1 条〕
- **他能做**：一键转任务（默认给最合适的岗位）、忽略、或"以后这类直接做，不用问我"（生成一条规则，需他确认）。
- **失败分支**：事件太多 → 聚合成一条摘要，不逐条推。

### S10 人在手机上发任务

- **他在哪**：微信私聊机器人。
- **他发**："把上周的报销单整理一下，周五前给我"。
- **系统回应**（微信里，短）：
  > 收到，我拆成 2 步：找单据 → 汇总成表。周五前给你。有需要你批的我会发这里。
- **关键约束**：微信限速 7 条/5 分钟 → 回复必须**合并**，不能每条进度都发。默认只发三类：收到、需要你、做完了。

### S11 离开 8 小时回来

- **他在哪**：打开 `/`。
- **他看到**（顶部一条，可折叠）：
  ```
  你不在的 8 小时：完成 6 件、失败 1 件、有 2 件等你
  〔看时间线〕〔只处理等我的 2 件〕
  ```
- **点开时间线**：按时间倒序，每条一行"谁 + 做了什么 + 结果"，可点进任务。
- **设计理由**：人回来第一需求是"有没有坏事"，不是"看全部细节"；所以先给结论（6/1/2），再给路径。

### S12 取消、改期、撤销

- **取消**：任务卡右下"停"→ 二次确认只说后果："已抓到的 2 个站点会保留，未开始的会取消。"〔确认停〕〔继续跑〕
- **改期**："周五前"改成"下周一"→ 直接对 Lead 说，Lead 更新任务并回一句"改到周一 18:00 前"。
- **误批更正**：审批后 30 秒内，回执消息上有〔改主意〕；超过 30 秒但动作尚未执行（排队中）也可撤；已执行则显示"已发出，无法撤回，要我发一条更正吗？"
- **撤销的边界必须提前说**：审批卡上永远有一行"发出后无法撤回"或"可在 30 秒内撤回"。

## 5. 屏幕规格与状态矩阵

### 5.1 `/` Now

| 区块 | 内容 | 规则 |
|---|---|---|
| 状态行 | "2 件等你 · 3 件在跑 · 一切正常" | 有红色风险时改为风险句；**不显示 0 计数** |
| 输入框 | placeholder："让谁做什么，什么时候要" | 支持语音、附件、@岗位 |
| 最近 3 条 | 最近的任务/对话 | 超过 3 条去 `/team` |

状态矩阵：

| 状态 | 显示 | 可做 |
|---|---|---|
| 空（首次） | S1 的三选一 | 绑定 / 跳过 |
| 空（日常） | "现在没有等你的事。队友在跑 2 件 →" | 派活 / 看团队 |
| 加载 | 骨架屏（不转圈超过 1 秒） | — |
| 断线 | 顶部黄条"与电脑断开，正在重连" + 输入框可打字但暂不发送 | 重试 |
| 模型不可用 | 输入框下方一行"模型连不上，消息会排队" | 重试 / 换模型 |
| 出错 | 一行"界面出问题了"+〔刷新〕，不显示堆栈 | 刷新 |

### 5.2 `/inbox` 等我

只有三类东西能进来：**审批**、**需要决策/缺东西**、**外部消息待处理**。进度、完成（无风险的）不进这里。

| 分组 | 排序 | 单条呈现 |
|---|---|---|
| 现在必须做（审批/阻塞） | 最旧优先（防饿死） | 一行动作 + 一行后果 + 三个动词 |
| 等我决定 | 按截止时间 | 一行问题 + 两个选项 + "先放着" |
| 外部消息 | 按来源分组 | 一行来源 + 摘要 + 转入任务 |

空态："没有等你的。有 3 件在跑 → 看团队"。

### 5.3 `/team` 在跑

- 顶部：一行汇总（"2 个岗位在跑，1 个空闲，1 个掉线"）。
- 列表：任务卡（三行制），按"卡住 > 进行中 > 排队"排序。
- 点开：`/t/:taskId`。
- 空态："还没有队友。第一次派活时会自动建一个。"

### 5.4 `/t/:taskId` 任务详情

固定五段，顺序不许变（人脑是按这个顺序问问题的）：

1. **在做什么**（标题 + 一行目标）
2. **到哪一步了**（状态 + 时间线，最近 3 条，可展开全部）
3. **证据**（来源链接、截图、命令输出，可预览）
4. **产物**（文件卡片，可下载/预览）
5. **要不要你**（没有就写"不需要你做什么"；有就给按钮）

### 5.5 `/c/:id` 会话

- 完成卡、审批卡、提问卡都内联，不弹模态。
- 队友的过程折叠在"这次派了 2 个队友"一行里，点开才看。
- 滚动：新内容贴底；用户上滚时不抢滚动。

### 5.6 设置（只列新增）

| 页面 | 内容 | 默认值 |
|---|---|---|
| `/settings/notifications` | 六类通知 × 渠道 × 免打扰 × 升级 | 审批=主渠道+站内+系统；其余=汇总 |
| `/settings/connectors` | 每个连接器状态、绑定用户、入站白名单、出站策略 | 群消息/邮件=每条必审 |
| `/settings/bots` | 岗位模板、工具授予、预算 | 只有"助理"一个 |

**首次进入设置**：每个字段下方一行小字"改了会怎样"，不给裸开关。

## 6. 任务卡的人话规范

### 6.1 三行制（强制）

```
第 1 行：<做什么>             <状态> · <谁> · <多久>
第 2 行：<现在具体在做什么 / 卡在哪>
第 3 行：<要不要你>（"不需要你做什么" / "等你批准" / "等你给个东西"）
```

规则：

- 第 1 行不超过 24 个汉字；第 2 行不超过 40 个；第 3 行不超过 16 个。
- 第 2 行**必须具体**：不许写"正在处理"，要写"正在抓 3 个站点，已完成 2 个"。
- 第 3 行只有三种句式：不需要你 / 等你 X / 需要你决定 Y。
- 状态词只用六个：排队中、进行中、等你、卡住、完成、失败。**不许**用"运行中/活跃/处理中"混着来。

### 6.2 颜色与语义（沿用现有 token 规则）

| 状态 | 语义色 | 说明 |
|---|---|---|
| 排队中 | 中性 | 灰，不抢眼 |
| 进行中 | 进行态（非警告） | 不许用黄色（黄色=要人动作） |
| 等你 | 提醒态 | 唯一允许抢眼的颜色 |
| 卡住 | 警告态 | 必须带"下一步"按钮 |
| 完成 | 中性 + 对勾 | 不用绿色大色块 |
| 失败 | 错误态 | 必须带"下一步"按钮 |

**强调色预算**：一屏最多 2 个填充块、1 个主按钮、2 个红色元素（沿用现有规则）。

## 7. 通知与打扰预算

### 7.1 分级

| 级别 | 内容 | 渠道 | 是否算打扰 |
|---|---|---|---|
| P0 阻塞 | 审批、队友卡住、外部消息要求立刻回 | 主渠道 + 站内 + 系统通知 | 算，且**必须**发 |
| P1 结果 | 完成/失败（有风险时） | 主渠道 | 算 |
| P2 汇总 | 进度、分诊结果、每日总结 | 汇总频道（每日 1–2 次或攒 5 条） | 不算 |
| P3 静默 | 心跳、重试、租约 | 只在 `/team` 可见 | 不算 |

### 7.2 打扰预算（这是人最需要的开关）

- 默认：**P0+P1 合计每天 ≤5 次**；超出后自动降级为汇总，并在汇总里说明"今天打断已达上限，剩下 3 条在这里"。
- 一键状态：**我在忙 2 小时**（P1 静音，P0 仍发）、**今晚别找我**（P0 也攒到明早，但要显式确认"可能有活卡到明早"）。
- 免打扰时段：默认 22:30–08:00（P0 也压住，早 8:00 一次性汇总）。

### 7.3 推送内容规范

- 标题必须是**动作**，不是"通知"：「批准：给张三发报价单」。
- 正文第一行是**后果**：「发出后无法撤回」。
- 必须能**不点开就做完**（短码或按钮）。
- 同一任务 10 分钟内最多推 1 条（合并）。

## 8. 审批交互规格

### 8.1 桌面（`/inbox` 第一条）

```
┌──────────────────────────────────────────────┐
│ 需要你批准                        2 分钟前    │
│ 给「张三」发报价单邮件（附件 3 个）            │
│ 发出后无法撤回                                │
│ 收件人 zhang@acme.com · 主题 报价单-v2         │
│ [拒绝]  [始终允许]              [允许并发送]   │
│ Esc = 拒绝 · Enter = 允许                     │
└──────────────────────────────────────────────┘
```

- **三个动词不中性化**（沿用现有规则）：允许 / 始终允许 / 拒绝；**没有默认动作**，Esc=拒绝。
- 「始终允许」必须显示它会记住什么：「以后给张三发邮件不再问我」+〔先只这一次〕。

### 8.2 手机与其他入口

**手机上看到的就是电脑上那一套**：内网直接打开同一个 Web，全功能模块都在，布局自适应（单列 + 底部标签栏）。

| 入口 | 你看到 | 你怎么批 |
|---|---|---|
| 微信 / 钉钉 / 飞书（文字） | 一段话：要做什么、后果是什么、回复同意或不同意 | 回「同意」/「不同意」 |
| 钉钉 / 飞书（应用机器人卡片） | 三按钮卡片 | 点按钮 |
| 桌面 Web / 手机 Web（内网） | `/inbox` 三按钮卡 | 点按钮 |

文字回复的规则（简单版）：

- 只有一条待批 → 「同意」直接生效。
- 多条待批 → 它先问「现在有 3 条，回 1 / 2 / 3」。
- 词表窄；看不懂就问编号，**绝不猜**。
- 只认你本人；引用/转发的「同意」不算。
- 30 秒内可回「改主意」撤回（未执行时）。

### 8.2b 每个渠道到底能干什么（按官方文档核对）

| 能力 | 微信 ClawBot | 钉钉 | 飞书 | 邮件 |
|---|---|---|---|---|
| 收消息 | ✅ 单聊 | ✅ 仅**应用机器人 + Stream** | ✅ 仅**应用机器人（长连接/回调）** | ✅ IMAP |
| 发通知 | ✅ 纯文本 | ✅ webhook（单向）或应用机器人 | ✅ webhook（单向）或应用机器人 | ✅ SMTP |
| 卡片按钮 | ❌ | ✅ 互动卡片（回调走 Stream 或 HTTP） | ✅ 卡片（自定义机器人只能跳链接，**不能回调**） | ❌ |
| 群聊 | ❌ 插件声明只支持单聊 | ✅ | ✅ | — |
| 限速 | 未公开（媒体实测约 7 条/5 分钟） | 200 次/分钟/会话 | 自定义机器人 100 次/分钟、5 次/秒；body ≤ 20KB | 取决于邮箱服务商 |
| 24 小时窗口 | **有**（超窗下发被丢弃，媒体实测） | 无 | 无 | 无 |

由此推出三条交互规则：

1. **微信只做单聊**：不设计"在微信群里 @ 机器人"这条路径；群里接活只能钉钉/飞书。
2. **微信有 24 小时窗口**：定时任务/夜间汇总可能在窗口外被丢弃 → 界面要显示"微信已超过 20 小时没有互动，结果改发邮件"。
3. **飞书/钉钉的"能点一下"必须用应用机器人**：用群自定义 webhook 时卡片按钮只能跳链接——所以"点按钮批准"在飞书上要么走应用机器人，要么退化成"点链接打开网页"。

### 8.3 过期与升级

| 时间 | 行为 | 用户看到 |
|---|---|---|
| 0 | 推 P0 | 「需要你批准」 |
| 15 分钟 | 换下一个渠道 | 新渠道里标「第二次提醒」 |
| 30 分钟 | 标"卡住"，进汇总置顶 | 「有一条批准等了 30 分钟，任务停在这里」 |
| 任务取消/过期 | 审批单作废 | 「这条已经不需要你了」 |

### 8.4 误批与更正

- 30 秒内：回执上〔改主意〕可撤（动作未执行时直接取消）。
- 已执行：给"发一条更正"的选项，不假装能撤回。
- 所有更正写进任务时间线，人能看到自己的决定历史（可追溯，不羞辱）。

## 10. 无障碍与可发现性

- 对比度：所有状态文字用 token 语义色，不靠颜色单独传达（图标 + 文字双编码）。
- 焦点：抽屉/模态打开时焦点陷阱，关闭后回到触发元素。
- 屏幕阅读器：任务卡三行分别有可读标签（"任务：研究竞品定价；状态：进行中；是否需要你：不需要"）。
- 零值常显：团队/子代理入口在零值也显示（可发现），但**不显示数字 0**（沿用现有验收 C6）。
- 缩放 200% 不出现横向滚动条；任务卡三行制在窄屏改为两行（第 2、3 行合并）。

## 11. 文案词典

### 11.1 禁用词（面向人的界面一律不出现）

| 禁用 | 换成 |
|---|---|
| 租约、心跳、CAS、修订号 | （不出现；需要时写"还在跑/已超时"） |
| 子会话、子代理 | 队友 |
| token 预算、配额 | 花销（"大约 4 万 token"可接受，原始计数不可） |
| 任务板、看板 | 在跑的事情 |
| 正在处理中 | 具体动作（"正在抓 3 个站点"） |
| 失败（单独出现） | 失败 + 原因 + 下一步 |

### 11.2 高频句式

- 收到 → 「收到。我拆成 N 步：… 要现在开始吗？」
- 等待 → 「等你批准」「等你给个东西」「等你决定」
- 卡住 → 「卡住了：<原因>。<两个出路>」
- 完成 → 「做完了：<结果一句话>。我没能确认的：<一句>。」
- 超时 → 「比预计慢，我还在跑，预计还要 N 分钟」
- 失败 → 「失败了：<原因>。你可以：<动作 1> / <动作 2>」

## 12. 交互验收清单（逐条可测）

**30 秒模式**
1. 手机锁屏收到审批，不点开消息也能在 15 秒内用短码批完。
2. 桌面 `/inbox` 第一条审批不滚动即可完成三个动词操作。
3. Esc 在任何审批态都是拒绝，且拒绝有可见回执。

**判断与信息**
4. 任一任务卡，不看详情就能回答"在做什么/卡在哪/要不要我"。
5. 任一失败卡都有至少一个可点的下一步。
6. 任一审批卡都有"后果"一行（可撤回/不可撤回）。
7. 任务卡第 2 行不出现"正在处理"这类空话（可用 lint 检查文案表）。

**离开与回来**
8. 离开超过 2 小时后回到 `/`，首屏给出"完成/失败/等你"三个数。
9. 点"看时间线"能在 3 秒内定位到失败那一条。
10. 汇总里每条都能一键跳到对应任务。

**手机**
11. 微信只发三类消息（收到/需要你/完成），进度不逐条推。
12. 微信一条消息不超过 120 字（限速下的合并策略）。
13. 非绑定用户回复"同意"不产生任何动作，且不回复对方。

**异常**
14. 断线时输入框可用（排队），恢复后消息不重复发送。
15. 模型不可用时给出"会排队"的明确说法，不丢消息。
16. 审批过期后推送一条"这条不需要你了"。
17. 误批 30 秒内可撤回，界面不假装已撤回。
18. 队友掉线 10 分钟后自动重派，人不需要操作。

**预算与打扰**
19. 当天第 6 次 P1 通知被降级为汇总，并说明原因。
20. "我在忙 2 小时"期间只发 P0。
21. 预算用到 80% 时给一次提示（只一次）。

**可发现性**
23. 零值的"团队"入口仍可见，但不显示 0。
24. 所有快捷键都有对应按钮。
25. 设置项下方都有"改了会怎样"的一句话。

**一致性**
26. 状态词只有六个（排队中/进行中/等你/卡住/完成/失败），没有同义词混用。
27. 进行中不使用警告色。
28. 一屏强调色不超预算（2 填充/1 主按钮/2 红）。
29. 任务详情五段顺序固定。
30. 所有时间用相对时间（"2 分钟前"），悬停显示绝对时间（含时区）。

## 13. 完整性矩阵（防遗忘的机械手段）

> 用法：**新增任何事件之前，先在表里加一行；代码里必须能找到对应的"人看到什么"。**

| 事件 | 谁会看到 | 在哪看到 | 能做什么 | 不设计的后果 |
|---|---|---|---|---|
| 任务创建 | 人（仅当需要确认） | `/team` 或一行征询 | 看 / 砍半 | 人不知道活开始了 |
| 任务开始 | 人（静默） | `/team` | 停 | 不知道在跑 |
| 任务进度 | 人（汇总） | `/team` | 催 | 焦虑 |
| 任务等待审批 | **人（P0）** | `/inbox` + IM | 允许/始终/拒绝 | 卡死 |
| 任务缺输入 | **人（P0）** | `/inbox` + IM | 去填/降级/停 | 卡死且不知道为什么 |
| 任务完成 | 人（P1，可关） | `/c/:id` 完成卡 | 打开/重核/存技能 | 不知道结果 |
| 任务失败 | **人（P1）** | `/team` 卡 + IM | 三种下一步 | 无法恢复 |
| 超预算 | **人（P0）** | `/inbox` | 追加/收尾 | 静默烧钱或静默停摆 |
| 外部消息到达 | 人（汇总） | `/inbox` | 转任务/忽略/建规则 | 漏活 |
| 外部消息需立刻回 | **人（P0）** | IM | 回复/转任务 | 客户流失 |
| 队友掉线 | 人（汇总） | `/team` | 无需操作（自动） | 以为在跑 |
| 连接器断线 | 人（P1） | `/settings/connectors` + 顶部条 | 重连 | 以为通知发出去了 |
| 审批过期 | 人（静默→汇总） | `/inbox` | 重新发起 | 猜为什么没批 |
| 记忆建议待审 | 人（汇总） | `/inbox` | 批准/驳回 | 规则悄悄变了 |
| 误批/更正 | 人（P1 回执） | 同审批渠道 | 改主意 | 不可逆事故 |
| 计划/技能草稿 | 人（汇总） | `/c/:id` | 存/改/丢 | 经验不沉淀 |
| 预算/用量异常 | 人（P1） | `/settings` + 汇总 | 调 | 账单惊吓 |

## 14. 明确不做（避免"看起来完整"）

- 不做统计仪表盘、不做"AI 心情"动画、不做任务进度百分比（假精度）。
- 不做"全部允许"、不做批量审批、不做审批代理。
- 不做会话内多级嵌套的团队面板（团队只在 `/team` 与任务卡）。
- 不做移动端独立 App（先做 IM + 手机浏览器）。
- 不做"自动帮你决定"的默认放行。
